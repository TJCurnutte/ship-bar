ship-bar · a design review method · by travis curnutte

ship at 9.7, not when it looks done

AI agents build websites fast, and they mostly look the same: glows, gradients, glass cards, a floating phone. This is the method I use to get past that. A separate reviewer agent scores every build out of 10, hands back ranked fixes, and nothing ships below 9.7.

what it is

Two parts. First, art direction rules the building agent follows, ending in a deslop pass. Second, a reviewer agent that never touches the code. It looks at screenshots at 1440px and 390px, runs Lighthouse, checks the console, checks for horizontal overflow, and scans computed styles for banned patterns. It returns a score and a list of fixes, most important first. The builder fixes the top items, ships a new build, and the reviewer scores it again from scratch.

The banned list: glows, gradients, glassmorphism, floating phones, bento grids, confetti, serif headlines, filler copy.

the method

  1. kill the category default

    No near-black with a glowing accent, gradient orbs, glass cards, floating tilted devices or sparkle-emoji ai.

  2. pick references

    Choose 2-3 real best-in-class sites that fit the product's mood.

  3. get a second opinion

    Ask another design-minded agent for a direction. Where you converge, that's the signal.

  4. write design.md

    Warm canvas, ink, hairlines, one accent for the primary action. A display face, a ui grotesk, mono for data. Spacing, radius, motion, do/don't lists.

  5. show the transformation

    The hero shows input becoming output within one second.

  6. use real imagery

    Real product ui as cropped cards with true data. Plain, specific copy.

  7. one signature motion

    Plus subtle fade-ups, respecting prefers-reduced-motion.

  8. deslop

    Gradient text, pill badge above the h1, identical icon grids, same fade everywhere, rounded-2xl plus shadow-lg, stock shadcn slate, centered-everything, hype words, fake testimonials.

  9. verify, then review

    Screenshots at mobile and desktop, Lighthouse, then a separate reviewer agent scores it before the owner sees it.

The content scan matters more than I expected. Real things it caught: debug strings shown to users, joke placeholder data, off-palette chips, duplicate rows, UTC timestamps where local time belonged, and contrast failures.

cohorts

For bigger projects I run a cohort: several reviewer agents, each with one narrow lens, for example fun, art, security and pitch. Each scores independently against its own bar, so one lens can't talk another out of a problem. Their fixes get merged into one list ranked by impact, and the work ships when every lens clears its bar.

A single generalist reviewer tends to average things out. Narrow lenses don't.

# Ship bar: design review for AI-built websites

## Build
1. Kill the category default. No near-black with a glowing teal/cyan/purple accent, gradient orbs, glass cards, floating tilted devices, or sparkle-emoji "AI".
2. Pick 2-3 real best-in-class reference sites that fit the product's mood.
3. Get a second opinion from another design-minded agent. Where opinions converge, follow them.
4. Write design.md at the repo root: a warm canvas, ink, secondary and hairline colors, ONE accent reserved for the primary action; a display face, a UI grotesk, and mono for data; spacing, radius, hairlines over shadows, motion rules, do/don't lists.
5. Hero = the product's transformation shown working (input becomes output) within one second.
6. Imagery: real product UI as cropped cards with true data. Copy is plain, specific, concrete.
7. Motion: one signature animation plus subtle fade-ups; respect prefers-reduced-motion.
8. Deslop before shipping: gradient text, pill badge above the H1, identical icon-card grids, same fade on everything, uniform rounded-2xl + shadow-lg, unmodified shadcn slate, centered-everything, hype words, fake testimonials.
9. Verify: screenshots at mobile and desktop, Lighthouse, then a reviewer agent scores it before the owner sees it.

## Review (separate reviewer agent; it never edits the repo)
- Screenshots at desktop 1440px and mobile 390px.
- Lighthouse: performance, accessibility, best practices, SEO.
- Console errors: zero.
- Horizontal overflow at 390px: none.
- Computed-style scan for banned patterns: glows, gradients, glassmorphism, floating phones, bento grids, confetti, serif headlines (if your design.md bans them), filler copy.
- Content checks: debug strings shown to users, joke placeholder data, off-palette chips, duplicate rows, raw UTC timestamps, contrast failures, sticky elements covering inputs.

Output: a score out of 10 plus fixes ranked most important first.
Ship bar: 9.7. Below it, the builder fixes the top items and the reviewer re-scores a new build.

## Cohorts (optional)
Run several narrow-lens reviewer agents (for example fun, art, security, pitch), each with its own bar, scoring independently. Merge their fixes into one list ranked by impact. Ship when every lens clears its bar.

faq

What is the ship bar method?

A way to review AI-built websites before a human sees them. A separate reviewer agent scores each build out of 10 from screenshots, Lighthouse and automated checks, returns ranked fixes, and the build only ships at 9.7 or above.

Why a separate reviewer agent?

The agent that built the page tends to grade its own work kindly. A reviewer that only reads screenshots and reports, and never edits the repo, keeps the score honest and the fixes specific.

What counts as vibe-coded?

The category defaults: glows, gradients, glassmorphism, floating phones, bento grids, confetti, decorative serif headlines and filler copy. The reviewer scans computed styles for these, not just the screenshot.

Why 9.7 and not 10?

9.7 was the point where the remaining notes were taste, not defects. Below it, there was always something a visitor would notice.

What are cohorts?

Several narrow-lens reviewer agents, for example fun, art, security and pitch, each scoring independently against its own bar. Their fixes are merged into one list ranked by impact.

Can a score go down?

Yes. In the example below, v13 scored 9.3 after v12 passed at 9.7, because a sticky call-to-action covered a form field and a gradient slipped in. Every build is re-scored from scratch.

How do I use it?

Copy the SKILL.md block into your agent's skills or instructions, write a design.md for your project, and run a second agent as the reviewer on every build.
